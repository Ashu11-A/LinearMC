# Fix for running out of direct memory

During sustained chunk generation (around 500 chunk reads and writes per second), every chunk read and write allocated a new direct (off-heap) buffer and nothing freed it at a known point. Allocation outpaced garbage collection until the limit was hit, and from then on every chunk read and write threw `OutOfMemoryError`. Generation froze, writes failed and TPS dropped while CPU stayed low. A restart cleared it, and full-speed generation brought it back within minutes.

## Fixes

- Reads free their direct buffer on `close()`.
- Write staging now uses the heap. Only the compressed image kept for each slot stays off-heap, sized to its compressed bytes.
- Closing a region frees those retained images right away.
- The V1 flush streams slots into the file instead of building one direct buffer of several MB. V2 and V3 already flushed without one, and all versions share the other fixes.

The format did not change. Replace the jars and you are done.

## Measured: v1.1.2 vs v1.1.3

Same server, seed and workload: Horizon on Paper 26.3, a Chunky circle of radius 2500, about 99,000 chunks.

### Stress run with the direct memory limit forced to 1G

This is a close-up of the failure, not a realistic setup. 1G means the JVM flag `-XX:MaxDirectMemorySize=1G`, which caps Java's direct (off-heap) memory at 1GB, 8x below the normal default. I used it only to make the failure show up in about a minute instead of about 13. Nobody needs to set it, and it does not belong in production. At 1G even the data that should be there (about 19k chunks at about 30KB each) fills the cap, so both versions stall. What differs is how they fail:

| | v1.1.2 | v1.1.3 |
|---|---|---|
| Out-of-memory errors | 1000+ | 39 |
| Failed chunk writes | 552 | 0 |
| Final generation rate | 0.1 chunks/s | 0.3 chunks/s |

### Normal run with the default 4G limit
